# Deploying to Render

One long-running container serving the Admin CMS, the public school websites and the API,
with a persistent disk so data survives restarts and redeploys.

| Path | Application |
| --- | --- |
| `/` | Admin CMS |
| `/site/…` | Public websites (`/site/school`, `/site/college`) |
| `/api`, `/swagger` | API, proxied through the Admin |

## Why a persistent disk is not optional

The database and uploaded media live on the disk mounted at `/data`. Without it the
container writes to its own temporary filesystem, which means:

- every restart or redeploy loses all saved data;
- if the service scales to more than one instance, each has its own copy, so two people
  testing at the same time see different content.

That is the whole reason a serverless profile does not work for this application.
**The Render free plan has no persistent disk — the Starter plan is the minimum.**

## Deploy

1. Push this repository to GitHub.

2. In Render: **New → Blueprint**, select the repository. Render reads `render.yaml` and
   creates the service, the disk and the environment variables.

3. Set one value in the dashboard before the first deploy finishes:

   | Variable | Value |
   | --- | --- |
   | `Seed__DemoAdminPassword` | the password the demo accounts will use |

   `Jwt__Key` is generated by Render automatically and stays stable across deploys.

4. Wait for the build. First boot installs the seeded demo database onto the disk, so the
   site is populated immediately.

Prefer to do it by hand? **New → Web Service → Docker**, set the Dockerfile path to
`./Dockerfile.render`, add a disk mounted at `/data`, and set the same variables.

## Redeploys and schema changes

The image carries a database built from that build's schema, plus a fingerprint of the
model. On start the entrypoint compares it with the disk:

- **same schema** — the existing database is kept, so your test data survives;
- **schema changed** — the old file is renamed to `cms.db.backup-<timestamp>` and the new
  seeded database is installed.

This is deliberate. SQLite here is created with `EnsureCreated`, which never alters an
existing database, so a redeploy that adds a column would otherwise leave the old file in
place and every page would fail with *"no such column"*.

**A release that changes the schema resets demo content.** Acceptable while a client is
testing; not acceptable once real content exists — see below.

## Going to production

Two changes, neither of which needs code:

1. **Move to SQL Server**, as the requirement specifies. Migrations then apply properly and
   nothing is reset:

   ```bash
   Database__Provider=SqlServer
   ConnectionStrings__DefaultConnection=<connection string>
   Database__ApplyMigrationsOnStartup=false   # run migrations as a deploy step
   ```

   ```bash
   dotnet ef database update --project src/Cms.Infrastructure --startup-project src/Cms.Api
   ```

2. **Move media to S3**, so uploads are not tied to one disk:

   ```bash
   Storage__Provider=S3
   Aws__AccessKey=…  Aws__SecretKey=…  Aws__Region=…  Aws__BucketName=…
   Aws__PublicBaseUrl=https://cdn.example.com
   ```

Also worth setting once real domains are involved:

```bash
Platform__DeploymentHost=<your-service>.onrender.com   # CNAME target shown in Domains
Platform__ServerIp=<A record target, if any>
PublicSite__BaseUrl=https://<your-service>.onrender.com/site
Seed__EnableDemoData=false                             # stop seeding demo content
```

## Custom domains

Add the domain in Render (Settings → Custom Domains) **and** in the CMS under
**Domains**, bound to the website it should serve. Render terminates TLS; the CMS decides
which school's site that host resolves to.
